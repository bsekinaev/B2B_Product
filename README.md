# B2B Product Content Generator

Локальный HTTP-прототип для подготовки **черновиков** товарных карточек
контрольно-измерительных приборов с GigaChat API. Разработан по тестовому
заданию на позицию AI-разработчика компании «СОЮЗ-ПРИБОР».

**Статус:** MVP 0.1.0. Работа API подтверждена; выполнение требования к длине
SEO-описаний на реальных демонстрационных запросах **не достигнуто**. Сервис
не публикует карточки автоматически. Детали — в [отчёте о приёмке](docs/ACCEPTANCE.md).

## Быстрый запуск (Windows / PowerShell)

Требуется Python **3.12**. Выполняйте команды из корня репозитория.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
Copy-Item .env.example .env
```

В `.env` заполните `GIGACHAT_CREDENTIALS` своим Authorization key и проверьте
`GIGACHAT_SCOPE` (PERS/B2B/CORP — в зависимости от доступа). Не публикуйте `.env`.
При ошибках доверия к TLS установите доверенный сертификат удостоверяющего центра
из официального источника и укажите путь к нему через `GIGACHAT_CA_BUNDLE_FILE`.
Нельзя отключать `GIGACHAT_VERIFY_SSL_CERTS` или менять URL на произвольный сервер.

Запуск:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Документация Swagger: http://127.0.0.1:8000/docs. Проверка сервиса:
`GET http://127.0.0.1:8000/health` → `{"status":"ok"}`.

## Генерация карточки

`POST /generate` принимает JSON с полями `name`, `manufacturer`, `specs`,
`description`. Первый пример — `examples/products/manometer.json` (DM 02 из PDF задания).
Второй пример — `examples/products/thermometer.json`: БТ-51.211 «РОСМА»,
маркировка и параметры проверены по [документации производителя](https://rosma.spb.ru/termometers/seriya_211_obschetehnicheskie_tylnoe/).
Это иллюстративный выбор, **не второй набор данных, полученный от работодателя**.
Ни один пример не является подтверждением доступности товара или его текущей цены.

В другом окне PowerShell при запущенном API:

```powershell
$Json = Get-Content -LiteralPath .\examples\products\manometer.json -Raw -Encoding UTF8
$Body = [System.Text.Encoding]::UTF8.GetBytes($Json)
Invoke-RestMethod -Uri "http://127.0.0.1:8000/generate" -Method Post `
    -ContentType "application/json; charset=utf-8" -Body $Body
```

Возвращается JSON с `status`, `card`, `missing_fields`, `warnings`.
В `card` находятся SEO-заголовок, SEO-описание, исходные характеристики,
3–5 поисковых запросов (цель) и коммерческий блок. Характеристики
копируются из входных данных программно, LLM их не переписывает.

| Статус | Значение |
|---|---|
| `ready_for_review` | Формальные проверки пройдены; **обязательна** ручная проверка |
| `requires_revision` | Недостаточная длина, предупреждения или другие проблемы качества |
| `insufficient_data` | Недостаточно структурированных технических характеристик |

При пустом/неверном JSON сервис отвечает контролируемой ошибкой.
Повторяющиеся JSON-ключи отклоняются; лимиты: **32 КиБ** на HTTP-тело и
**16 КиБ** на нормализованные данные. Сообщения об ошибках провайдера
не раскрывают ключ или текст стороннего исключения.

## Промпты и принятые решения

- `app/llm/prompts.py`: системные редакторские правила и отдельный пользовательский
  JSON с исходными данными. Текст товара не считается инструкцией для модели.
- GigaChat формирует **только текстовые поля** по строгой JSON-схеме.
  Технические значения и статус остаются под контролем Python-кода.
- `app/validation.py`: детерминированные проверки SEO-заголовка (до 70 символов),
  описания (800–1200 символов), уникальности 3–5 поисковых запросов,
  пропусков и части неподтверждённых технических утверждений.
- Допускается один дополнительный редакторский вызов для слишком короткого
  описания, когда есть достаточное количество исходных характеристик.
  Итого **не более двух генераций на товар** без учёта внутренних сетевых повторов SDK.
- `ready_for_review` не означает, что семантическая достоверность доказана.
  Текст проверяет контент-менеджер, автоматически ничего не публикуется.

## Тестирование и примеры результатов

Автоматическая приёмка без сети и API-ключа:

```powershell
.\.venv\Scripts\python.exe -m pytest -q --cov=app --cov-branch --cov-report=term-missing
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m scripts.run_acceptance
```

Проверка доступа и короткой текстовой генерации (потребляют/могут потреблять
API-квоту):

```powershell
.\.venv\Scripts\python.exe -m scripts.check_gigachat_access
.\.venv\Scripts\python.exe -m scripts.check_gigachat_completion
```

Проверка двух реальных товаров с агрегированным отчётом, **до четырёх
GigaChat-вызовов**, плюс внутренние сетевые повторы SDK:

```powershell
.\.venv\Scripts\python.exe -m scripts.run_acceptance --live --report
```

Для сдачи нужны примеры **самих результатов**, а не только метрики.
Команда ниже отдельно и явно выполняет live-генерацию для двух тестовых
товаров, сохраняет полные черновики в `examples/results/` и **не скрывает**
предупреждения. Перед `git add` обязательно просмотрите оба файла:

```powershell
.\.venv\Scripts\python.exe -m scripts.export_live_examples --confirm-live
```

После экспорта выполните **формальную проверку обоих ответов** без дополнительных
вызовов API:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_live_results
```

Для экспорта в другую папку можно передать `--dir artifacts/pr1_live`.
Проверка отклоняет пустой коммерческий блок, слишком короткое описание,
неизменённые предупреждения и несоответствие характеристик. Успешный
результат не заменяет проверку фактического смысла контент-менеджером.

Без `--confirm-live` генерация и запись не выполняются. Если файлы уже
существуют, команда откажется их перезаписывать. В каждый результат добавляется
маркер `review_status: human_review_required`: это **примеры работы API,
а не утверждённые рекламные описания**. Никогда не включайте в репозиторий
реальные закрытые сведения о продукции. `artifacts/` с техническими метриками
исключён из Git.

## Ограничения и развитие

- В реальной приёмке 3 ноября 2026 года модель выдала для демонстрационных
  товаров описания на **282 и 412 символов** при требовании 800–1200;
  оба результата получили `requires_revision`. Это известное отклонение от ТЗ,
  а не успешная SEO-приёмка.
- Длина текста не должна достигаться вымыслом или повторами. Для надёжного
  выполнения норматива нужны дополнительные проверенные сведения из паспортов
  изделий и редакторское ревью.
- Числовые и словарные эвристики не гарантируют отсутствие смысловых ошибок,
  ложных свойств или неверных связей между характеристиками.
- Приложение предназначено **только для локального использования**. Внешнее
  развёртывание требует аутентификации, ограничения частоты запросов и
  отдельной оценки обработки коммерческой информации.
- Нет БД, CMS, очередей и автоматической публикации: для прототипа они не нужны.

Подробная матрица требований, результаты тестирования и остаточные риски:
[docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).
