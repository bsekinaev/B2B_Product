# B2B Product Content Generator

Я разработал небольшой HTTP-сервис для подготовки черновиков товарных карточек контрольно-измерительных приборов. Это тестовое задание на позицию AI/LLM-разработчика в компании «СОЮЗ-ПРИБОР». Для генерации текстов я использую GigaChat API; входные характеристики сохраняю программно, без переписывания моделью.

**Состояние проекта:** тег `v0.1.0` опубликован 3 ноября 2026 года. HTTP API, установка и обработка ошибок проверены. Редакторские требования ТЗ **выполнены не полностью**: реальные SEO-описания оказались короче нормы, а коммерческие блоки — пустыми. Исправления разрабатываю отдельными коммитами; готовность карточки к публикации не заявляю. Подтверждённые результаты и оставшиеся отклонения описаны в [отчёте о приёмке](docs/ACCEPTANCE.md).

## Что я реализовал

Я принимаю JSON с названием, производителем, характеристиками и необязательным описанием товара. Через GigaChat формирую SEO-заголовок, SEO-описание, поисковые запросы и коммерческий блок. Ответ отдаю как структурированный JSON со статусом и предупреждениями.

Технические параметры я **не поручаю генерировать модели**: поле `specifications` копируется из исходного объекта `ProductInput`. Проверки вынес в `app/validation.py`, работу с GigaChat — в `app/llm/client.py`, правила генерации — в `app/llm/prompts.py`.

Стек: Python 3.12, FastAPI, Pydantic 2, pydantic-settings, GigaChat SDK, pytest, Ruff.

## Установка и запуск

Проверял проект на Windows с Python 3.12.3. Команды ниже выполняются в корне репозитория:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
Copy-Item .env.example .env
```

В `.env` нужно указать свой `GIGACHAT_CREDENTIALS` и проверить `GIGACHAT_SCOPE`. Доступные значения — `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B`, `GIGACHAT_API_CORP`; выбранный scope должен соответствовать учётным данным. **Не добавляйте `.env` в Git.**

Проверку TLS я оставил обязательной. Если системе не хватает доверенного сертификата, нужно получить сертификат удостоверяющего центра из официального источника и указать путь через `GIGACHAT_CA_BUNDLE_FILE`. Отключение проверки TLS и произвольные адреса API запрещены настройками.

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Документация API: http://127.0.0.1:8000/docs. Проверка доступности: `GET /health` возвращает `{"status":"ok"}`. Сервис рассчитан на **локальный запуск**, не на открытый интернет.

## Пример запроса

Используйте файл `examples/products/manometer.json`:

```powershell
$Json = Get-Content -LiteralPath .\examples\products\manometer.json -Raw -Encoding UTF8
$Body = [System.Text.Encoding]::UTF8.GetBytes($Json)
Invoke-RestMethod -Uri "http://127.0.0.1:8000/generate" -Method Post `
    -ContentType "application/json; charset=utf-8" -Body $Body
```

`POST /generate` принимает следующие поля:

| Поле | Что передаю |
|---|---|
| `name` | Название прибора, обязательно |
| `manufacturer` | Производитель, обязательно |
| `specs` | Словарь характеристик с исходными значениями |
| `description` | Необязательное текстовое описание |

Ответ содержит `status`, `card`, `missing_fields`, `warnings`. В `card` находятся `seo_title`, `seo_description`, `specifications`, `search_queries` и `commercial_note`.

| Статус | Что он означает |
|---|---|
| `ready_for_review` | Формальные ограничения пройдены; карточка **всё ещё требует проверки человеком** |
| `requires_revision` | Обнаружены нарушения требований к содержанию или формату |
| `insufficient_data` | Не хватает структурированных технических характеристик |

Валидацию входа я сделал до обращения к GigaChat: отклоняются повторяющиеся JSON-ключи, неверные типы и слишком большие запросы. Предел HTTP-тела — 32 КиБ; нормализованного объекта — 16 КиБ. Текст ошибок провайдера и ключ доступа в HTTP-ответ не передаются.

## Как устроена генерация

В `app/llm/prompts.py` я передаю модели правила и отдельно JSON с данными товара. Модель должна вернуть только четыре текстовых поля. Если описание слишком короткое и исходных сведений достаточно, генератор может сделать **один** дополнительный редакторский запрос. Всего — не более двух генераций на товар, не считая сетевых повторов SDK.

В `app/validation.py` я проверяю заголовок до 70 символов, описание от 800 до 1200 символов, число и уникальность 3–5 поисковых запросов, пустой коммерческий блок, отсутствующие значения и ряд рискованных утверждений. После восьмого этапа добавил распознавание отдельных неподтверждённых формулировок о высокой точности, долговечности и областях применения.

**Это эвристические проверки, а не полноценный фактчекинг.** Например, упоминание числа из источника ещё не означает, что модель связала его с правильной характеристикой. Поэтому даже статус `ready_for_review` не разрешает автоматически публиковать текст.

## Тестирование

Основные команды не требуют API-ключа и не обращаются к GigaChat:

```powershell
.\.venv\Scripts\python.exe -m pytest -q --cov=app --cov-branch --cov-report=term-missing
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m scripts.run_acceptance
```

На чистой копии опубликованного `v0.1.0` проверил установку с нуля: **207 тестов PASS**, покрытие 98%, Ruff и пять офлайн-сценариев PASS. После исправления валидатора в этапе 8 получил **214 тестов PASS**, покрытие 98% в основном Windows-окружении. Чистую установку уже с изменениями этапа 8 пока не повторял. Единственное предупреждение тестов относится к устаревающему использованию `httpx` в Starlette TestClient; на результат проверок оно не повлияло.

При наличии собственных реквизитов GigaChat можно отдельно проверить подключение:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_gigachat_access
.\.venv\Scripts\python.exe -m scripts.check_gigachat_completion
```

Следующие команды выполняют реальные вызовы и **расходуют API-квоту**:

```powershell
.\.venv\Scripts\python.exe -m scripts.run_acceptance --live --report
.\.venv\Scripts\python.exe -m scripts.export_live_examples --confirm-live
```

Экспорт сохраняет два полных ответа в `examples/results/` и помечает их `human_review_required`. Файлы **исключены из Git** и не входят в опубликованный релиз. Примеры входных данных `manometer.json` и `thermometer.json` — демонстрационные; это не проверенные паспорта товаров. В частности, текущий пример манометра не совпадает с обозначением DM 02, фигурировавшим в исходном задании: эту сверку ещё необходимо завершить.

## Что пока не выполнено по ТЗ

В последнем сохранённом live-прогоне GigaChat вернул описание манометра длиной **290 символов**, термометра — **412 символов**. Требование — **800–1200 символов**. В обоих ответах коммерческий блок пуст, а статус — `requires_revision`. Дополнительно в описании термометра были неподтверждённые утверждения о свойствах и применении прибора, которые прежний валидатор не обнаружил.

Я не считаю успешный HTTP-запрос доказательством качества карточки и не дополняю текст вымышленными свойствами ради количества символов. Для окончательной сдачи ещё нужны содержательные SEO-тексты, проверенные коммерческие блоки и **два полных примера выходных JSON** в согласованном комплекте материалов. Обязательна ручная проверка технического смысла.

Текущие результаты, источники проверки и ограничения фиксирую в [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).
