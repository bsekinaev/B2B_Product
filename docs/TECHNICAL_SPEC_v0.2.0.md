# Техническое задание v0.2.0 — каталог товаров, исполнения и происхождение данных

**Версия ТЗ:** 1.0  
**Дата:** 8 ноября 2026 года  
**Исходная база:** опубликованная v0.1.3; `main` `8c6f61a8a596cd0b428998481947f84c5b48e4b3`.  
**Ветка разработки:** `feat/v020-catalog-foundation`.  
**Статус:** работа по этапам; релиз v0.2.0 не заявлен до полной приёмки.  
**Связанный аудит:** [контрольная точка](AUDIT_v0.2.0_BASELINE.md).

## 1. Цель и ценность

Перейти от одиночного локального генератора к **проверяемому каталогу B2B-товаров**, в котором у каждой характеристики определены принадлежность (серия/исполнение), исходное значение и источник. Это основа для массовой генерации, редакторских ревизий и повторяемой оценки качества. Версия 0.2.0 не является готовым публичным SaaS.

## 2. Объём релиза

- Типизированные записи источников, характеристик, товарных серий и выбранных исполнений.
- PostgreSQL как источник истины; SQLAlchemy 2.x для моделей/репозиториев и Alembic для версионируемых миграций.
- Категории/определения характеристик, товары/исполнения, значения характеристик, источники. Исходные значения сохраняются без подмены нормализованными.
- Начальные `generation_jobs`, `card_revisions`, `claim_evidence` и `review_events` проектируются и мигрируются как база будущих этапов; **полноценный редакторский UI и фоновый worker не входят**.
- Повторяемый локальный импорт существующих проверенных JSON-товаров с provenance; не выполнять сетевых запросов к `catalog_reference`.
- Безопасное чтение каталога и подготовка `ProductInput` для действующего генератора без изменений `POST /generate`.
- Тесты, документация, миграция вверх/вниз, демонстрационный сценарий.

## 3. Инварианты данных

**CAT-01 — идентичность:** товар определяется стабильным UUID и проверяемой парой производителя/каталожного идентификатора в пределах выбранного источника. Нельзя объединять разные исполнения на основании одного названия.

**CAT-02 — серия и исполнение:** `series` и `configured_variant` различаются явно. Атрибуты исполнения нельзя молча считать общими для всей серии. Для выбранного исполнения требуется его обозначение/имя.

**CAT-03 — исходное значение:** `raw_value` хранится отдельно от `normalized_value`, оригинал никогда не изменяется вследствие генерации. Пустые значения допустимы для неполных импортируемых записей, но не считаются доказанными фактами.

**CAT-04 — проверяемый источник:** у значимого атрибута есть ссылка на `source_id`. Источник содержит вид, название и HTTPS-ссылку либо SHA-256 локального документа. Ссылки сохраняются как метаданные, **не запрашиваются автоматически**. Нельзя прикрепить несуществующий источник.

**CAT-05 — принадлежность атрибута:** значение относится ровно к одному субъекту — товару (серии) или варианту исполнения. На уровне БД обеспечить `CHECK`/FK и уникальность по определению характеристики и области.

**CAT-06 — история:** отдельные ревизии карточки не переписывают источник и прежние утверждения. Миграции данных не уничтожают историю.

**CAT-07 — безопасность:** входы и импорты ограничены по размерам, файлы не могут выйти за разрешённый каталог; `.env`, ключи, сырые токены GigaChat не хранятся в карточках, журналах и репозитории.

**CAT-08 — обратная совместимость:** `GET /health`, `POST /generate`, существующие `ProductInput`, `GenerationResult`, статусы и `generation_meta` сохраняются без обязательных новых полей.

## 5. База данных: минимальная схема

Первичный набор из дорожной карты `ARCHITECTURE_PLAN.md`:
- `product_categories` — код категории, русское название, версия схемы.
- `attribute_definitions` — определение характеристик, тип, единица, обязательность, ограничения.
- `products` — UUID, производитель, название, источник/артикул, категория, исходное описание.
- `product_variants` — UUID, товар, обозначение исполнения и статус конфигурации.
- `sources` — UUID/код, вид, HTTPS-URI или хеш документа, название и время фиксации.
- `attribute_values` — FK на определение/источник, исходное и нормализованное значение, ссылка на `product_id` XOR `variant_id`.
- `generation_jobs` — статус, `idempotency_key`, версия промпта, источник модели, `input_hash`.
- `card_revisions` — ревизия и снимок JSON; `editorial_status` как данные, без утверждения через UI.
- `claim_evidence`, `review_events` — задел для редакторского контроля.

Для PostgreSQL использовать `JSONB`, миграции Alembic. **Запретить** дублирующие ссылки на одну и ту же характеристику в одной области и удаление используемого источника без явного решения. Особое внимание — `NULL` при уникальных ограничениях.

## 6. API и импорт

Текущий `POST /generate` не становится зависимым от БД. Все новые операции работают локально до отдельного решения о внешнем доступе. Для V020-04 реализовать чтение одного товара/исполнения и экспорт проверенного `ProductInput` без генерации и без публикации.

Для импорта использовать `examples/live_batch/manifest.json` как исторический источник идентификаторов, ссылки и `source_scope`. Не приписывать источнику доказательства на уровне атрибута без явной проверки. При отсутствии достоверного соответствия `source_id` отмечать факт как требующий дополнения, а не выдавать его за подтверждённый.

Повторный импорт с тем же входным хешем должен быть идемпотентным. При изменении данных — новая версия/отказ с диагностикой, без тихого перезаписывания.

## 7. Нефункциональные требования и тесты

- Python 3.12; Windows и Ubuntu, детерминированные офлайн-тесты по умолчанию.
- Покрытие с ветвлениями не ниже 95%; Ruff lint/format, `pip check`, существующая офлайн HTTP-приёмка, 24 синтетических сценария — PASS.
- Отдельные интеграционные тесты PostgreSQL в CI после введения БД; SQLite не заменяет проверку PostgreSQL CHECK/JSONB.
- Проверить ошибочные URL, пользовательские реквизиты в URI, некорректные хеши, дубль источника/атрибута, неизвестные `source_id`, конфликт `series/variant`, несоответствие `raw_value` входным `specs`, откат транзакций.
- Секреты и реальный GigaChat не требуются для CI. Нельзя вызывать GigaChat в тестах без явного разрешения.
- Коммиты/PR — на русском языке. Не изменять `main`, опубликованный тег `v0.1.3` и исторические JSON до прохождения проверок и отдельного релизного решения.

## 8. Ограничения и отложенные этапы

`v0.3.0`: CSV/Excel, Celery/Redis, пакетная обработка, устойчивые очереди.  
`v0.4.0`: роли `admin/editor/viewer`, редакторские ревизии, `draft → in_review → approved`, экспорт только одобренного.  
`v0.5.0`: LLMOps, стоимость/токены, длительности p50/p95, распределённые лимиты и эксплуатация.

Вне v0.2.0: публичный SaaS, CMS-развёртывание, микросервисы, Kubernetes, автоматическая публикация карточек. Доказательная редакторская оценка ≥4/5 остаётся отдельной задачей и не заменяется unit-тестами.

## 9. Решение о готовности

Каждый инкремент допускается к PR только после собственных тестов. Для релиза v0.2.0 требуются все V020-01–V020-05 и отдельный отчёт приёмки; до этого исходная релизная версия пакета остаётся `0.1.3`.
