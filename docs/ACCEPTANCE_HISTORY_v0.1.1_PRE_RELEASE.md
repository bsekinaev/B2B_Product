# Проверка B2B Product Content Generator по ТЗ

**Дата проверки:** 3 ноября 2026 года.
**База:** `main`, коммит `e47fbf4`.
**Кандидат релиза:** `v0.1.1` (тег пока не создан).

## Что я реализовал

Я разработал локальный FastAPI-сервис для подготовки B2B-карточек
измерительных приборов. Он принимает JSON, проверяет входные данные,
вызывает GigaChat API, формирует текстовые разделы и возвращает
структурированный результат.

Технические характеристики в выходном JSON берутся из входных данных,
а не из ответа LLM. Для проверки текста используются ограничения длины,
количества запросов, предупреждения о неподтверждённых утверждениях
и проверка повторяющихся предложений.

Для ответов недостаточного качества я добавил ограниченный редакторский
повтор и детерминированный fallback из исходных характеристик.

## Реальные обращения к GigaChat

Я проверил GigaChat API на двух демонстрационных товарах и двух
самостоятельно подобранных каталоговых примерах. Ответы модели
неоднократно не проходили редакторскую приёмку: SEO-описания
оказывались слишком короткими, а некоторые формулировки содержали
неподтверждённые преимущества или неправильную привязку свойств.

Это подтверждает необходимость независимой проверки.

## Два примера для сдачи

В `examples/submission/` сохранены исходные данные, JSON-результаты
и `provenance.json` с указанием происхождения. Оба результата получены
офлайн-воспроизведением сохранённых ответов GigaChat с применением
детерминированного fallback.

| Товар | SEO, символов | Статус |
|---|---:|---|
| МЕТЕР ДМ 02 (серия) | 1131 | ready_for_review |
| РОСМА БТ-51.211 | 1063 | ready_for_review |

В обоих случаях я подтвердил неизменность структурированных
характеристик, заполненность коммерческого блока, допустимую длину
SEO-заголовка, 3–5 поисковых запросов и отсутствие предупреждений
автоматического валидатора.

Результаты не означают, что две карточки были написаны GigaChat
без участия fallback. Их происхождение явно обозначено.

- Характеристики без изменения — подтверждено.
- 3–5 поисковых запросов — подтверждено.

- Недостаток сведений — отражается в статусе и списках проблем.
- Ошибки входного JSON и API — проверяются тестами.

В исходном PDF приведён только один неполный демонстрационный товар.

## Ограничения

Автоматические правила не обеспечивают полного смыслового фактчекинга.
Даже `ready_for_review` требует редакторской проверки.

Fallback может формировать текст в техническом, а не маркетинговом
стиле. При недостатке фактов сервис не обязан искусственно достигать
800 символов.

Локальный MVP не включает аутентификацию клиентов, rate limiting,
хранение данных, CMS и автоматическую публикацию. Публично
развёртывать HTTP-сервис без дополнительных мер защиты нельзя.

4. Отправить локальные коммиты в `origin/main`.
5. Создать тег `v0.1.1` только после успешной проверки.
6. Передать ссылку на репозиторий и краткое описание работодателю.

  и предел измерения;
