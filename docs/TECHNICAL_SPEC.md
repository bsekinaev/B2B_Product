# Техническое задание: B2B Product Content Generator

**Статус:** базовое ТЗ развития. **Основа:** v0.1.1 (commit 2c51135). **Ближайшая версия:** v0.1.2.
**Принцип:** опубликованный v0.1.1 неизменяем; каждый завершённый этап — коммит на русском, изменения через PR.
**Назначение:** развитие открытого проекта, созданного для тестового задания. Нельзя утверждать внедрение у работодателя без подтверждения.

## 1. Цель
Стабилизировать сервис подготовки черновиков карточек контрольно-измерительных приборов. GigaChat генерирует текст, но исходные технические характеристики остаются неизменными и принадлежат входным данным. Результат не публикуется автоматически и требует редакторской проверки.

Ближайший v0.1.2 — качество, безопасность, воспроизводимость и CI, без изменения JSON-контракта.
**Вне объёма v0.1.2:** PostgreSQL, Celery/Redis, CMS, GUI, авторизация для публичного доступа, RAG, мультиарендность, автоматическая публикация.

## 2. Исходное состояние и подтверждённые проблемы
- Python 3.12 / FastAPI / Pydantic / GigaChat SDK; 280 тестов PASS, 96% branch coverage; 24 синтетических сценария.
- Два демонстрационных результата подготовлены через офлайн-воспроизведение и deterministic fallback, а не через новую удачную генерацию live LLM. Требуется human review.
- На main v0.1.1 отсутствует каталог .github/workflows; предыдущие успешные Actions не тестировали его текущий commit.
- pyproject.toml: version=0.1.1; app/main.py: FastAPI version=0.1.0.
- README и docs/ACCEPTANCE.md содержат устаревший статус «релиз ещё не опубликован».
- В конфигурации не все ValidationError маппятся на контролируемую HTTP-ошибку.
- При непустом description, но пустых specs возможен бессмысленный запрос к LLM.
- Простая эвристика назначения может превратить отрицание в положительное утверждение.
- Сопоставление числа по всем входным данным не подтверждает его связь с конкретным свойством.
- Live acceptance проверяет HTTP-контракт, но может завершиться успешно даже с requires_revision.

## 3. Функциональные требования v0.1.2

### REL-01 / P0 — CI
Автоматически запускать GitHub Actions при push в main и рабочие ветки, а также PR в main. Матрица Ubuntu/Windows + Python 3.12. Проверки: установка, pip check, Ruff lint, Ruff format, pytest branch coverage >=95%, HTTP-offline acceptance и синтетические 24 сценария. Отсутствие секретов GigaChat в CI — требование. Неверный результат любого шага завершает workflow с ошибкой. Включение обязательной branch protection — отдельная ручная настройка репозитория.

### REL-02 / P1 — версия
Метаданные пакета и OpenAPI.info.version должны совпадать; исключить ручную строку 0.1.0 в app/main.py. Добавить регрессионный тест. Версию 0.1.2 фиксировать перед выпуском, а не в первом черновом коммите.

### DOC-01 / P1 — документация
Обновить README, docs/ACCEPTANCE.md, docs/REVIEWER_GUIDE.md и release notes, не удаляя историю исходного задания. Явно отделить: fake LLM; offline replay реальных записанных ответов; live GigaChat; редакторскую проверку. Не заявлять, что две карточки прошли живую генерацию без fallback. Не указывать будущий релиз как опубликованный.

### API-01 / P1 — конфигурация
Невалидные настройки (scope, TLS, base URL и пр.) не должны давать необработанный HTTP 500. Для POST /generate: контролируемый HTTP 503 и JSON-код configuration без ключей, тела стороннего исключения и traceback. GET /health остаётся доступен без GigaChat credentials. Проверить через HTTP с подменёнными переменными окружения.

### GEN-01 / P1 — недостаток технических сведений
Если в specs нет ни одного непустого значения, GigaChat не вызывается, даже при заполненном description. Отдать HTTP 200, бизнес-статус insufficient_data, missing_fields и соответствующее предупреждение. Проверить spy/mock провайдером на ноль обращений и неизменность specs.

### GEN-02 / P1 — отрицания
Извлечение назначения не должно переинтерпретировать «не предназначен для измерения», «не для измерения», «не используется для измерения», «не подтверждено использование для измерения» как подтверждённое назначение. При сомнении пропускать заявленное назначение. Проверить положительные и отрицательные случаи. Не заявлять общий NLP-фактчекинг на базе regex.

### VAL-01 / P1 — привязка свойств к значениям
Не считать любое число из исходного товара подтверждением его использования в другом свойстве. Ввести консервативные проверки очевидных пар: диапазон — значение/единицы, диаметр — значение/единицы, класс точности — значение, резьба — обозначение. Подмена значения приписанной характеристике вызывает warnings и requires_revision в поддерживаемом наборе; корректные примеры не отклоняются. Точные границы поддержки описать в коде и документации.

### QA-01 / P1 — live quality gate
Отдельные результаты HTTP_CONTRACT и CONTENT_QUALITY. Live-ответ 200 с requires_revision — корректный HTTP, но не успешная редакторская приёмка. Строгий режим завершать ненулевым кодом при непройденном quality gate; live запускается только явно и потребляет квоту. Отчёт хранит режим, дату, модель, статус, длины, предупреждения без секретов.

### SEC-01 / P1 — сохранение защитных инвариантов
Обязательный TLS, официальный API URL, предел тела запроса и нормализованного JSON, запрет дублирующихся ключей, отдельная обработка ошибок GigaChat, невывод секретов. Отказ от автоматической публикации и от ложных рекламных обещаний.

## 4. Контракт, который сохраняется
GET /health и POST /generate, а также OpenAPI /docs. Вход: name, manufacturer, specs и nullable description. Выход: status, card (seo_title, seo_description, specifications, search_queries, commercial_note), missing_fields, warnings. Смысл ready_for_review — допустим для ручной проверки, но НЕ утверждён редактором.

Пустые технические характеристики: HTTP 200 и insufficient_data (не исключение провайдера). Ошибки входа: 413/415/422. Ошибки провайдера: 429/502/503/504 по действующей карте. Несовместимые изменения контракта запрещены без отдельного решения и версии.

## 5. Нефункциональные условия
- Python 3.12; чистый запуск на Windows и Ubuntu.
- Unit/HTTP-тесты и CI выполняются без сети GigaChat и без доступа к секретам.
- Синхронный SDK не блокирует event loop.
- Не хранить ключи, токены и полные сырые исключения в логах, ответах и отчетах.
- Не добавлять зависимости без необходимости и отдельной проверки.
- Редакторская достоверность не выводится из 96% coverage.
- Публикация и изменение тега v0.1.1 запрещены.

## 7. Приёмочные критерии
- A01: матрица Windows/Linux и Python 3.12 проходит pytest >=95% branch coverage, Ruff, pip check, HTTP-offline и синтетический batch.
- A02: GitHub Actions показывает зелёные результаты для актуального PR head SHA.
- A03: версия OpenAPI и установленного пакета совпадает; неизменность опубликованного тега подтверждена.
- A04: неверные настройки дают безопасный 503; GET /health работает без токена.
- A05: specs={} и непустой description не вызывают LLM.
- A06: четыре типа отрицания не превращаются в назначение; две положительные карточки сохраняют назначение.
- A07: подмена значения между диапазоном и диаметром обнаружена, существующие примеры не отклонены.
- A08: HTTP_SUCCESS не маскирует CONTENT_QUALITY_FAILURE в live режиме.
- A09: CI не требует токенов и не выполняет реальные вызовы внешней модели.
- A10: README/инструкция/релизные заметки не противоречат коду, истории и происхождению примеров.

Релиз готов, если A01–A10 подтверждены тестами, журналами и diff. Live-генерацию обозначать только по фактически проведённым вызовам.

## 8. Риски
Regex не заменяет понимание контекста; отсутствие технических данных не позволяет без выдумки получать 800–1200 символов; исполнение серии нельзя принять за готовый артикул; fake provider не доказывает качество живой LLM. Права на коммерческую документацию и лицензию проверить перед расширением публикации.
