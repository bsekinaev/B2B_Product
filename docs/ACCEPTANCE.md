# Проверка B2B Product Content Generator по ТЗ

**Дата фиксации:** 3 ноября 2026 года. **Опубликованная версия:** `v0.1.0`, коммит `9fe396f`. **Состояние разработки:** проверка рекламных утверждений зафиксирована коммитом `2111630` в `main`, но пока не входит в тег `v0.1.0`.

Я разделяю техническую и редакторскую приёмку. Сервис успешно устанавливается, обрабатывает JSON и обращается к GigaChat. При этом **полного соответствия требованиям к готовому товарному тексту пока нет**.

## 1. Что требовалось и что я проверил

| Требование задания | Фактический результат |
|---|---|
| Принимать JSON товара или предоставлять форму | Реализовал `POST /generate` с Pydantic-схемой; веб-форма не нужна при наличии JSON API |
| Использовать LLM API | Подключил GigaChat SDK, проверил реальные HTTP-вызовы |
| SEO-заголовок до 70 символов | Добавил проверку длины и наличия названия товара |
| SEO-описание 800–1200 символов | Проверка есть, но **оба последних live-результата требованиям не соответствуют** |
| Характеристики товара без вымысла | Исходный словарь `specs` копируется без изменений; текст модели проверяется лишь частично |
| 3–5 поисковых запросов | Проверяю количество, пустые значения, дубли и базовую релевантность |
| Коммерческий блок: кому и для каких задач | Поле реализовано, но в обоих последних live-результатах оно **пустое** |
| Обозначать отсутствующие сведения | Добавил `insufficient_data`, `missing_fields`, `warnings`; ошибки обязательных HTTP-полей пока имеют общий код `invalid_product` |
| Контролировать ошибки и не хранить ключ в коде | Реализовал безопасные коды ошибок, локальную конфигурацию и обязательную проверку TLS |
| Представить результаты двух товаров | Добавил входные примеры и экспорт; **два проверенных выходных JSON в релизе отсутствуют** |
| Дать инструкцию запуска и объяснить промпты | Описал запуск, формат API, правила генерации и ограничения в README |

**Отдельная незакрытая сверка:** файл `examples/products/manometer.json` в `v0.1.0` содержит демонстрационный МП-01, а не DM 02 производителя «Манотомь», фигурировавший в исходном задании. Пример термометра также условный. Эти данные нельзя представлять как подтверждённые паспортные сведения.

## 2. Проверки кода и установки

### Опубликованная версия `v0.1.0`

Я клонировал репозиторий в отдельную временную папку Windows, создал новое окружение Python 3.12.3 и установил зависимости через `pip install -e ".[dev]"`.

Результаты чистой установки:

- **207 тестов PASS**, покрытие приложения с ветвлениями **98%**.
- Ruff lint и Ruff format — PASS; `pip check` — PASS.
- Все пять офлайн-сценариев HTTP-приёмки — PASS.
- Технические характеристики в сценариях не изменяются.
- Репозиторий после тестов остаётся чистым.

### Этап 8: дополнительная проверка маркетинговых заявлений

В основном Windows-окружении я добавил распознавание отдельных неподтверждённых заявлений о высокой точности, долговечности, надёжности и специфическом применении. Регрессионные тесты проверяют как отклонение таких заявлений, так и случай, когда назначение указано в структурированных характеристиках.

**Результат текущего локального прогона:** 214 тестов PASS, покрытие 98%, Ruff lint и format PASS. Чистую установку с этим изменением пока не проводил. Изменение зафиксировано коммитом `2111630` («Усилена проверка неподтверждённых рекламных утверждений»).

Наблюдал одно предупреждение совместимости Starlette TestClient с `httpx`. Тесты оно не прервало.

В предыдущих запусках длина описания манометра отличалась (в одном из отчётов — 282 символа). **Для сверки с экспортированными JSON использую последнее зафиксированное значение 290**.

В описании термометра модель дополнительно заявила надёжность, долговечность, пригодность для лабораторных исследований, высокоточность и работу в труднодоступных местах. Во входных данных подтверждения этим словам нет. Изначальный валидатор не выделил их отдельным предупреждением. В этапе 8 я добавил узкие словарные проверки, но они не равнозначны полноценному фактчекингу.

Файлы с полными ответами хранятся локально в `examples/results/`, исключены из Git и **не включены в `v0.1.0`**. Пять офлайн-сценариев показывают работу HTTP-контракта, а не маркетинговую пригодность текста: их содержимое формируется тестовыми заглушками.

## 4. Ограничения и порядок закрытия

1. **SEO-описание.** Получить 800–1200 символов без повторов и без новых недоказанных фактов. Если исходных сведений недостаточно, сохранить статус `requires_revision`, а не заполнять длину «водой».
2. **Коммерческий блок.** Обеспечить осмысленный текст о применении и аудитории только на основе предоставленных фактов; не придумывать гарантию, сертификаты, сроки и совместимость.
3. **Достоверность.** Проверить связи между характеристиками и заявленными свойствами; нельзя считать перечисление известных чисел доказательством правильного смысла.
4. **Демонстрационные материалы.** Сверить пример манометра с исходным ТЗ, уточнить второй товар и подготовить два полных проверенных выходных JSON для передачи работодателю.
5. **Повторная приёмка.** После исправлений запустить тесты, Ruff, чистую установку и реальные GigaChat-вызовы; отдельно прочитать тексты вручную.

`ready_for_review` означает только прохождение автоматических проверок и необходимость дальнейшего просмотра человеком. Приложение не публикует карточки автоматически. У публичного HTTP-доступа нет аутентификации и ограничителя частоты: текущий способ запуска рассчитан только на локальную среду. Для внешнего использования понадобятся отдельные меры защиты.

**Мой итог на эту дату:** техническая часть MVP работает и воспроизводится. SEO- и редакторские требования **ещё не закрыты полностью**. Не выдаю HTTP 200 и успешные модульные тесты за подтверждение качества товарного текста.
